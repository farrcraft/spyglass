# 0038. How release archives are built

- Status: Accepted
- Date: 2026-10-28
- See also: [0003](0003-cargo-xtask-for-project-commands.md), [0008](0008-game-derived-test-values-stay-local.md), [0034](0034-an-exact-toolchain-bumped-deliberately.md), [0037](0037-versions-and-releases.md)

## Context

[ADR 0037](0037-versions-and-releases.md) decided what a release is. This decides how its archives are made, which brings several constraints:

- **Nothing of Mojang's may ship.** An archive is the easiest place for a stray bundle, jar or oracle output to leak out, and once it's on a release page it's redistributed.
- **CI only calls `cargo xtask`,** so every step can run locally ([ADR 0003](0003-cargo-xtask-for-project-commands.md), [ADR 0028](0028-supported-versions-and-ci.md)). `cargo-dist`, the common tool for this, generates its own workflow and owns the build steps.
- **The binaries are for people without Rust.**
  - On Windows, the MSVC target links the Visual C++ runtime dynamically by default, which a clean machine may not have.
  - On Linux, a binary needs a glibc no newer than the user's.
  - The viewer loads its windowing and GPU libraries at run time.
- **Release binaries embed paths** from the build machine (in panic messages and debug info), including the builder's home folder.
- **Every dependency's license must travel with the binaries.** That's 300-odd crates, under the licenses `deny.toml` allows, among them OFL fonts.
- **Signing costs money or accounts.** That's an Apple Developer ID for notarization, and a certificate or a signing service on Windows. Unsigned binaries get a Gatekeeper prompt on macOS and a SmartScreen warning on Windows.

## Decision

We will build release archives with **`cargo xtask dist [--target <triple>]`**, which the release workflow calls on one runner per target:

1. **Build** `spyglass`, `spyglass-viewer` and `spyglass-extract` with the `dist` profile (fat LTO, one codegen unit), `--locked` and the pinned toolchain ([ADR 0034](0034-an-exact-toolchain-bumped-deliberately.md)).
2. **Targets:**
   - `x86_64-pc-windows-msvc`, on `windows-2025`, with the C runtime linked statically (`+crt-static`);
   - `x86_64-unknown-linux-gnu`, on `ubuntu-22.04`, the oldest hosted image, to keep the glibc requirement low;
   - `aarch64-apple-darwin` and `x86_64-apple-darwin`, both on `macos-15`.

   More targets are added by a change to this list, not a new ADR.

3. **Remove build machine paths** with `--remap-path-prefix` for the workspace, `CARGO_HOME` and the toolchain. Set `SOURCE_DATE_EPOCH` from the commit.
4. **Archive deterministically:** `spyglass-<version>-<target>.zip` on Windows, `.tar.gz` elsewhere, with a fixed file order, timestamps and permissions.
5. **Check before writing:**
   - Only an allowlist of file names may enter an archive.
   - No binary may contain the workspace, `CARGO_HOME` or home folder paths.
6. **Ship third-party notices** as `THIRD-PARTY-LICENSES.html`, generated by `cargo-about`. Its accepted licenses are kept equal to `deny.toml`'s by a test.
7. **Don't sign, for now.** The release carries `SHA256SUMS` and a GitHub build provenance attestation per archive (`actions/attest-build-provenance`), which ties each archive to the workflow run and commit that built it. The first-run guide in each archive explains the OS warnings. Revisit when a free signing route for open-source projects is practical for the owner, or when users report the warnings as a real obstacle.

## Consequences

- The same command builds an archive on a laptop and in CI, and the allowlist guards both.
- `cargo xtask dist` is our code to maintain, roughly what `cargo-dist` would have given us: archive writing, target flags and checks. It's also only as clever as we make it. There are no installers, no updater and no package manager manifests.
- `cargo-about` is a new tool, pinned and installed only for releases (the setup scripts' release-tools option), not for everyday development.
- Static CRT makes Windows binaries slightly larger and needs no runtime installed.
- Building on `ubuntu-22.04` ties the Linux build to an image GitHub will retire. When it goes, the oldest remaining image raises the glibc floor, or the build moves to a container.
- Intel macOS is cross-compiled from Apple Silicon and runs under Rosetta in its smoke test, never on Intel hardware in CI.
- Unsigned binaries mean every Windows and macOS user sees a warning on first run, and some will stop there. Provenance and checksums help users who check them, which most won't.
- Reproducibility is checked by building one tag twice. Remaining differences are recorded here once known.

## Alternatives considered

- **`cargo-dist`:** less code of ours, with installers and package manager support. But it generates and owns the release workflow, which breaks the rule that CI only calls `cargo xtask`, and its archive contents are harder to guard with our own allowlist.
- **`cargo install` from git as the only distribution:** no release machinery at all, but it still needs Rust, which is what releases exist to avoid.
- **musl for Linux:** a fully static binary with no glibc floor. But the viewer's GPU and windowing stack loads system libraries at run time, which musl binaries can't do reliably.
- **Signing from the start:** fewer warnings for users, but it means paying for, or applying for, certificates before the first release, for a project with no users yet.
