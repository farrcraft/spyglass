# 0076. The oracle drives the game's portal code on a running server

- Status: Proposed
- Date: 2026-11-15
- See also: [0015](0015-locate-checks-on-a-real-server.md), [0033](0033-the-oracle-accepts-the-eula-only-when-asked.md), [0073](0073-the-oracle-joins-a-stand-in-player.md)

## Context

Which portal a trip lands at ([portals.md](../specs/portals.md)) depends on gameplay code, not on generation: the target block from the entity's position and the border, then `PortalForcer.findClosestPortalPosition` over the dimension's points of interest. Every other oracle command reads what the generator makes. This one needs a level with portal blocks in it, a POI manager that knows about them, per-dimension borders, and an entity to send through.

Two things make it awkward:

- `getPortalDestination` returns only a `TeleportTransition`, the position the entity ends up at. It doesn't say which exit block the game searched from or which portal block it found, and the landing position alone can't tell apart two adjacent portals or say where in a tie the game went.
- A trip that finds no portal makes the game build one (`createPortal`), frame and platform included. A built portal changes every later case near it.

## Decision

We will play the cases on the stock dedicated server, started in the harness's JVM and found as `Join` finds it ([ADR 0073](0073-the-oracle-joins-a-stand-in-player.md)). `spyglass.oracle.Portals` will:

- replace each `ServerLevel`'s private `portalForcer` field, by reflection, with a subclass of `PortalForcer` that calls the game's own `findClosestPortalPosition` and `createPortal` and notes their arguments and answers;
- per layout: set the borders named with `WorldBorder.setCenter` and `setSize`, place portal blocks with `Level.setBlock` (no neighbour updates, so no frame is needed), which adds their POIs as play does, and add stale records with `PoiManager.add` over a non-portal block;
- answer searches with the level's `findClosestPortalPosition`, and trips with `NetherPortalBlock.getPortalDestination` for a marker entity at the trip's position;
- set to air the portal blocks the game built after each trip, and undo every layout: the placed blocks, the stale records, the borders.

The game adds and removes a block's record in a later task (`updatePOIOnBlockStateChange` hands it to `MinecraftServer.execute`), so setting up, answering and undoing are each a server task of their own.

The cases are generated by the xtask from a fixed generator. The Overworld is a void superflat, whose dimension type, scale and heights are the Overworld's, so chunks load and generate quickly.

## Consequences

- The target, the search and its POI bookkeeping are the game's. The harness only chooses where portals are and reads the answers through the recording subclass.
- Reflection on a private final field depends on the JDK allowing it. JDK 26's final-field restrictions (JEP 500) warn and may later refuse; the run then fails at once, saying the forcer wasn't replaced.
- `getPortalDestination`'s use of the entry portal (the relative landing position) isn't checked: spyglass doesn't answer it.
- Built portals leave their obsidian frame and platform behind. They hold no POIs, so later searches don't see them, but the terrain is changed.
- The Nether isn't flattened, so portals placed there replace terrain. The search doesn't look at blocks other than the records' own, so that doesn't change answers.
- Like `locate` and `order`, it runs the server, so it needs the EULA accepted ([ADR 0033](0033-the-oracle-accepts-the-eula-only-when-asked.md)) and isn't part of `oracle golden`. It takes about 20 seconds, so CI runs it, as it runs `locate`.

## Alternatives considered

- **Reading the landing position** from the `TeleportTransition` and matching it to a placed portal: no reflection, but it can't separate adjacent portals or show the block chosen, and `createDimensionTransition` may move the position out of the portal to find free space.
- **Calling `findClosestPortalPosition` only**, with exits computed by the harness: no reflection, but the target computation would be the harness's copy of the game's code, which is half of what's under test.
- **One isolated area per case**, without cleanup: no removal code, but every case would generate new chunks in all three dimensions, and a missed overlap between cases would go unnoticed.
- **A normal Overworld:** the same answers, but each search loads up to 17 × 17 chunks and each built portal generates terrain, which takes several times longer.
